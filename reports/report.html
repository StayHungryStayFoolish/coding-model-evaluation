About this report

This report does not represent official Google evaluation data or conclusions. It summarizes results from tests on existing coding business scenarios to inform technology selection.

Scores come from compilation and execution, functional tests, regression tests and instruction checks. There is no primary or secondary judge model. GPT-6 Astra (reasoning level: high) assisted data review and report analysis; it did not score model answers.

How testing works: Models receive the same tasks and acceptance criteria within each track. Direct API code is generated before checks run. Engineering sessions can use public-check feedback to repair code; hidden functional checks and instruction constraints determine final acceptance. Both tracks use three runs. Antigravity uses separately archived tool-based results. Read the method · Public report and results

TL;DR

Argon’s strengths: trustworthy tests, effective repairs and complex code delivery

Tests are organized around practical business requirements across the main stages of the coding lifecycle, including complex tasks such as concurrent transactions, state management, compiler implementation and cross-language migration.

  • Specific quality advantages over Opus: In API unit test generation, Argon accepted correct implementations in all three runs; Opus produced a false failure once because of an incorrect expected value. In long-codebase repair, Argon’s patches fixed every target defect, while one Opus patch missed its location and left a rate-limiting fault. The practical advantage is fewer false test blocks and repairs that actually take effect.
  • Complete delivery of complex systems: Argon delivered a Rust/Wasm compiler that compiled and ran in all three runs, matching Opus’s functional result at 48.9% lower cost. Sonnet encountered a compilation error, while Haiku did not produce a complete artifact within the fixed output budget. In transaction storage evolution, Argon also had fewer version-compaction and conflict-check failures than each Claude model.
  • Cost value versus Opus: On this task set at the current promotional effective price, Argon cost 44.5% less per successful API scenario and 52.1% less per successful engineering task. Business selection should consider acceptance success and completion cost together, not token price alone.
  • Recommended development combination: Antigravity + Argon. This combination met the unambiguous requirements of all 21 tested scenarios, correctly handling telemetry inputs, post-recovery anomaly decisions and service recovery state. It is a practical choice for everyday coding, evolving requirements and code maintenance.

Business selection: establish acceptance quality, then compare completion cost

A lower token price does not guarantee a lower total cost for the same business outcome. More tokens do not guarantee a proportional increase in success. Delivery also depends on finding a correct solution, detecting errors through verification, and deciding whether failures need further repair, another model or human intervention.

Direct API full-success rates were 88.89% for Argon, 82.54% for Sonnet and 74.60% for Haiku. Argon led by 6.35 and 14.29 percentage points, respectively. The business difference is clearer in specific tasks: Argon completed the Rust/Wasm compiler in all three runs, while Haiku reached the output limit in all three without a complete artifact. Argon’s generated tests accepted correct implementations in all three runs, while Sonnet produced false failures twice. Average token prices alone cannot turn these failed outcomes into working deliverables.

The reported cost per successful task already allocates measured failure and feedback-repair costs. It is not a quote for successfully completing every requirement in the same batch. Sonnet and Haiku still cost less on the measured task set; the incremental cost of repairing their remaining failures to reach Argon’s current success level has not been measured. With engineering feedback, Sonnet and Argon both completed every session and Haiku completed 35 / 36, reinforcing the need to choose by workload.

Research context: The benefit of additional computation depends on task difficulty, the model and how solutions are verified. In mathematical reasoning experiments, the hardest tasks gained little from extra computation. Coding experiments show that more candidates can improve coverage, but reliably identifying a correct answer is critical. Research also shows that repeated attempts by smaller models can be competitive when effective unit tests are available. See the papers and findings in the Appendix.

Business implication: for complex delivery, first choose models that meet the key acceptance requirements, then account for API calls, verification, rework and human effort. This report does not count unmeasured rework as Argon savings or interpret failure within a finite budget as permanent model incapability.

Appendix · Evaluation basis

Scenario composition, scoring and comparison conditions

This report uses a custom task set designed around coding business needs, with task specifications, initial code, execution environments and acceptance checks. It compares specific development capabilities. It is neither an industry success-rate estimate based on randomly sampled customer production traffic nor an official Google benchmark.

The scenarios span the main stages of the coding lifecycle, combining common work such as logs, caches, interfaces and builds with complex transactions, state management, compilers and cross-language migration. Different scenarios test these stages separately. Controlled engineering tasks allow an edit-check-repair feedback loop; this is not a single production project tested end to end across its entire lifecycle.

Archive and scoring review notes

Prompts, generated code, execution records, scores and file checksums are retained for review against the final archive. The pre-run manifest has gaps in coverage of some check files, and frontend dependency files differ from their pre-run versions. The checksum manifest therefore does not establish independent pre-run freeze verification for every artifact. This report uses consistent final scoring, retains original and corrected results, and does not equate archive verification with independent third-party certification.

Public materials: The GitHub repository provides the bilingual report, methodology, scenario catalog, sanitized numerical results and an aggregation script. Original prompts, code submissions, hidden tests and execution logs are not included in this release. Recomputing summaries is different from rerunning the complete model evaluation.

Research: how additional computation affects success and business cost

These studies explain relationships between model selection and budget. They examine different models from the four in this report and are not used to estimate their specific success rates or costs.

  1. Returns depend on task difficulty. In mathematical reasoning experiments, Snell et al. found that the best additional-compute strategy varied with difficulty, and the hardest tasks gained little. The business implication is to select models and computation strategies by task, rather than treating extra budget as a proportional increase in capability. Scaling LLM Test-Time Compute Optimally (2024; §1, §7).
  2. Repeated attempts help, but coverage does not grow linearly with sample count. On SWE-bench Lite, Brown et al. increased DeepSeek-Coder-V2-Instruct from one sample to 250, improving coverage from 15.9% to 56%. Identifying and verifying correct solutions is critical to converting candidates into working deliverables. Sample counts are not token or cost multiples. Large Language Monkeys (2024).
  3. Effective tests can also make smaller models economical. Hassid et al. compared code generation under matched budgets. Repeated smaller-model outputs improved results when unit tests could select correct candidates; without tests, ranking those candidates fell short of a larger model’s single output. Model and verification quality should therefore be assessed together, rather than inferring cost from model tier alone. The Larger the Better? (COLM 2024).

These studies support both “more tokens may not close a task-specific capability gap” and “repeated attempts can be economical on verifiable tasks.” The measured results of the four models remain this report’s main selection evidence.
